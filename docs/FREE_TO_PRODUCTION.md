# Free → production migration

This document is the operator's runbook for moving Haven from the local
free-tier setup to a paid production deployment. The application is built so
that **only the environment configuration and the external provider accounts
change** — the frontend, the email pipeline, the SMS pipeline, the admin panel,
the database schema, and the API all stay the same.

> The free / local setup is the default. Production is just the same code with
> different environment variables and a different PostgreSQL / Redis / S3 /
> carrier footprint behind it.

---

## 0. Honest guard rails

The `/admin/system-health` page and the `/admin/launch-checklist` page surface
the same configuration facts at all times. The launch checklist refuses to
report "Production Ready" until every **critical** item is verified:

| Critical item                                    | What the page checks                                            |
| ------------------------------------------------ | --------------------------------------------------------------- |
| Production database configured                    | `pingDb()` succeeds                                             |
| Strong `AUTH_SECRET`                             | length ≥ 32, not a `.env.example` placeholder                   |
| Strong `CRON_SECRET`                             | length ≥ 16, not a placeholder                                  |
| HTTPS in production                              | `APP_URL` starts with `https://`                                |
| Cookies secure in production                     | `COOKIE_SECURE=true`                                            |
| Email provider configured                        | `EMAIL_INBOUND_PROVIDER` is not `mock`, signing key is real     |
| Email domain configured                          | `EMAIL_DOMAINS` is a real domain (not `your-domain.com`)        |
| MX records verified                              | at least one `ACTIVE` domain with `mxOk: true`                  |
| Email webhook verified                           | the configured adapter reports `ready: true`                     |
| SMS provider configured                          | `SMS_PROVIDER` is not `mock`, real credentials are present      |
| SMS webhook verified                             | the configured adapter reports `ready: true`                     |
| Storage configured                               | the configured driver loads without throwing                    |
| Stripe configured (if `PAYMENT_PROVIDER=stripe`) | `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are real        |
| Rate limits enabled                              | the `RateLimitRule` table has rows                              |
| Retired seed domains disabled                    | unowned .com domains from previous seeds are `DISABLED`         |

The launch checklist refreshes on every visit; it never claims success based
on a stale snapshot.

## 1. Free / local setup (the default)

```bash
git clone <repo>
cd temp-maill
cp .env.example .env
npm install
npm run db:seed
npm run dev
```

This boots with:

| Concern       | Free / local value                                     |
| ------------- | ------------------------------------------------------ |
| Database      | `DATABASE_URL="file:./dev.db"` (SQLite)                 |
| Cache         | `REDIS_URL=""` (in-process memory fallback)            |
| Email         | `EMAIL_INBOUND_PROVIDER=mock` (development adapter)     |
| SMS           | `SMS_PROVIDER=mock` (reserved-range pool, dev only)     |
| Storage       | `STORAGE_DRIVER=local` (filesystem under `database/data/attachments`) |
| Payments      | `PAYMENT_PROVIDER=manual` (JazzCash / Easypaisa / bank) |
| Ads           | `ads.test_mode=true` (no third-party tags render)      |
| CAPTCHA       | `CAPTCHA_PROVIDER=none`                                |
| OAuth         | unset — email + password only                          |
| Analytics     | `ANALYTICS_PROVIDER=internal`                          |
| Secrets       | `.env` only, generated by `node scripts/write-env.mjs` |

The dev server is reachable at `http://localhost:3000`. Hot reload is
enabled, the in-process job scheduler runs every minute, and SSE-driven
inbox updates work without a separate process.

### What the dev setup **does not** do

* It does not receive real internet email — the mock adapter's pool uses
  reserved 555-01xx and 7700-900xxx numbers and the email mock never
  receives public webhooks.
* It does not send real SMS — same reason.
* It does not serve real Stripe webhooks — manual payment is the only
  payment path.
* It does not pull third-party ad units — `ads.test_mode=true` keeps the
  layout but renders placeholders only.

These are enforced in code, not just in the seed. The mock adapters throw
`Errors.providerDown("SMS")` / `Errors.providerDown("Email")` in production,
and `isDomainAssignable()` refuses to mark a `.test` domain as assignable
when the real adapter is selected.

## 2. Production migration

The following table is the complete swap list. Every row is the same
Haven codebase — only the configuration changes.

| Concern       | Free (dev)         | Production                                                 | Where to set it               |
| ------------- | ------------------ | ---------------------------------------------------------- | ----------------------------- |
| Database      | SQLite             | Managed PostgreSQL (Neon, Railway, RDS, Supabase)          | `DATABASE_URL`                |
| Cache         | in-process memory  | Upstash / managed Redis                                    | `REDIS_URL`                   |
| Email         | `mock`             | Mailgun / Postmark / SMTP                                  | `EMAIL_INBOUND_PROVIDER` + provider keys |
| SMS           | `mock`             | Twilio / Telnyx / Vonage                                   | `SMS_PROVIDER` + provider keys |
| Storage       | `local`            | S3-compatible (R2, MinIO, Backblaze, AWS S3)               | `STORAGE_DRIVER=s3` + `S3_*`  |
| Payments      | `manual`           | Stripe                                                     | `PAYMENT_PROVIDER=stripe` + Stripe keys |
| Ads           | test mode          | AdSense / GAM with a real client id                        | `/admin/ads`                  |
| CAPTCHA       | `none`             | Cloudflare Turnstile / hCaptcha                            | `CAPTCHA_PROVIDER` + provider keys |
| OAuth         | disabled           | Google / GitHub                                             | `GOOGLE_CLIENT_ID` etc.       |
| Analytics     | internal           | internal (default) — Plausible / Umami sit alongside        | env, then wire at the proxy    |
| Secrets       | `.env` (mode 0600) | platform secret manager (never Git)                        | platform-specific             |

> The frontend, the admin panel, the inbox UI, the API, the database
> schema, the middleware, and every component are **unchanged** between
> free and production.

### 2.1 Database: SQLite → PostgreSQL

The Prisma schema in `database/prisma/schema.prisma` is the production
contract. It works against both SQLite and PostgreSQL.

```bash
# Production
# 1. Provision managed Postgres. Copy the connection string.
# 2. Set DATABASE_URL="postgresql://user:pass@host:5432/haven?schema=public"
# 3. In database/prisma/schema.prisma, set provider = "postgresql"
# 4. Apply the schema (use prisma migrate, not db:seed — that script
#    also creates the local SQLite file).
npx prisma migrate deploy --schema=database/prisma/schema.prisma
```

For local development, the project runs on SQLite via a built-in
`node:sqlite` shim that mirrors the Prisma API; this shim is
intentional and only loaded locally so production deploys can use the
official Prisma client against Postgres.

### 2.2 Cache: memory → Redis

`REDIS_URL` is read by `lib/redis.ts`. When unset, the module is a
process-local in-memory store that satisfies the same interface. When
set, the same code paths hit real Redis.

```bash
# Upstash (free tier, serverless-friendly):
REDIS_URL="rediss://default:<token>@<host>.upstash.io:6379"
```

The migration is purely a configuration change. The rate limit module,
SSE fan-out, settings cache, and webhook delivery queue all use the
same `cache.*` calls.

### 2.3 Email: mock → Mailgun / Postmark / SMTP

Switching providers is a configuration change. The application routes
through a single `InboundEmailProvider` interface; the implementation
is selected at boot from `EMAIL_INBOUND_PROVIDER`.

```bash
# Mailgun
EMAIL_INBOUND_PROVIDER=mailgun
MAILGUN_API_KEY=key-...                              # Mailgun REST API
MAILGUN_WEBHOOK_SIGNING_KEY=<mailgun signing key>    # HMAC-SHA256
MAILGUN_DOMAIN=mail.your-domain.com

# Postmark
EMAIL_INBOUND_PROVIDER=postmark
POSTMARK_SERVER_TOKEN=<server token>
POSTMARK_WEBHOOK_USER=<basic auth user>
POSTMARK_WEBHOOK_PASS=<basic auth password>

# SMTP (custom receiver)
EMAIL_INBOUND_PROVIDER=smtp
SMTP_HOST=mail.your-domain.com
SMTP_PORT=587
SMTP_USER=<smtp user>
SMTP_PASS=<smtp password>
EMAIL_EXPECTED_MX=mail.your-domain.com
```

**The API key and the webhook signing key are not interchangeable.**
The API key is for Mailgun REST operations; the signing key is for
verifying inbound webhook HMACs. Haven checks both and reports them
separately in `/admin/email-providers`.

#### DNS records

For Mailgun, point your domain at the Mailgun MX servers and add the SPF
record. At your registrar:

| Type | Host | Value                              |
| ---- | ---- | ---------------------------------- |
| MX   | `mail.your-domain.com` | `10 mxa.mailgun.org` and `10 mxb.mailgun.org` |
| TXT  | `mail.your-domain.com` | `v=spf1 include:mailgun.org ~all` |

In the Mailgun dashboard, create a Receiving route that matches the
recipient pattern and forwards to:

```
https://haven.your-domain.com/api/webhooks/mailgun/inbound
```

Re-run `npm run db:seed` after the DNS propagates so the domain's
`mxOk` flag is computed from a real DNS lookup. Or open
`/admin/domains → Verify MX`.

### 2.4 SMS: mock → Twilio / Telnyx / Vonage

```bash
# Twilio
SMS_PROVIDER=twilio
TWILIO_ACCOUNT_SID=AC...
TWILIO_AUTH_TOKEN=...
TWILIO_WEBHOOK_AUTH=<your chosen basic-auth secret>

# Telnyx
SMS_PROVIDER=telnyx
TELNYX_API_KEY=KEY...
TELNYX_PUBLIC_KEY=<base64 ed25519 public key>

# Vonage
SMS_PROVIDER=vonage
VONAGE_API_KEY=...
VONAGE_API_SECRET=...
```

Each adapter enforces its own signature verification on the inbound
webhook (`/api/webhooks/<provider>/sms`); see the launch checklist
for the exact URL to paste on the carrier console.

Mock numbers use reserved 555-01xx and 7700-900xxx ranges; real
provider numbers are obtained by the provider's own inventory APIs and
are never fabricated in code.

### 2.5 Storage: local → S3-compatible

```bash
STORAGE_DRIVER=s3
S3_ENDPOINT=https://<accountid>.r2.cloudflarestorage.com
S3_REGION=auto
S3_BUCKET=haven-attachments
S3_ACCESS_KEY=<access key>
S3_SECRET_KEY=<secret key>
```

The local driver remains available for staging. Application code does
not change — `StorageDriver.put / get / delete` is the only contract.

### 2.6 Payments: manual → Stripe

```bash
PAYMENT_PROVIDER=stripe
STRIPE_SECRET_KEY=sk_live_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_PUBLISHABLE_KEY=pk_live_...
```

The Stripe webhook URL is:

```
https://haven.your-domain.com/api/v1/payments/stripe
```

`PAYMENT_PROVIDER=manual` is preserved for regional rails (bank
transfer, JazzCash, Easypaisa). Both adapters satisfy the same
`PaymentProvider` interface.

The admin `/admin/payments` page exposes the Stripe keys as
"configured (hidden)" — secrets are never displayed in the admin UI.

### 2.7 Ads: test → production

1. Sign up for the ad network of your choice (AdSense, GAM, etc.).
2. Open `/admin/ads` and set the network client id.
3. Disable `ads.test_mode`. The placement is rendered with the real
   network's tags.

Ad placements are described in `docs/advertising.md`. Ad slots
deliberately avoid the generator button, the inbox list, the OTP
copy button, and any payment control.

### 2.8 CAPTCHA: none → Turnstile / hCaptcha

```bash
CAPTCHA_PROVIDER=turnstile
TURNSTILE_SITE_KEY=<public site key>
TURNSTILE_SECRET_KEY=<server-side secret>
```

The site key is rendered on the client; the secret is verified
server-side and never sent to the browser.

### 2.9 OAuth: none → Google / GitHub

```bash
GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...
GITHUB_CLIENT_ID=...
GITHUB_CLIENT_SECRET=...
```

Either set works. The login page surfaces a button only when at least
one provider is configured.

## 3. Environment variable priority

The order is:

1. **Environment variables** (highest priority, server-side only).
2. **Database / admin configuration** (DB-driven, can be edited in
   the admin panel; covers non-secret knobs like plan limits,
   retention, ad placements, etc.).
3. **Safe schema defaults** (the `config/env.ts` zod schema provides a
   sane fallback for every variable).

Critical security secrets **never** migrate from the env into the
admin panel:

* `AUTH_SECRET`
* `DATABASE_URL`
* `MAILGUN_API_KEY` / `MAILGUN_WEBHOOK_SIGNING_KEY`
* `POSTMARK_SERVER_TOKEN` / `POSTMARK_WEBHOOK_USER` / `POSTMARK_WEBHOOK_PASS`
* `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET`
* `S3_SECRET_KEY`
* `TWILIO_AUTH_TOKEN` / `TELNYX_API_KEY` / `VONAGE_API_SECRET`
* `CRON_SECRET`

The admin panel can show whether each of these is **configured** (a
boolean) and the runtime health endpoint reports it, but the value
itself is never rendered.

## 4. Pre-deploy checklist (matches `/admin/launch-checklist`)

- [ ] Production database configured (`DATABASE_URL` set, migrations applied)
- [ ] Email provider configured (`EMAIL_INBOUND_PROVIDER` + keys)
- [ ] Email domain configured (`EMAIL_DOMAINS` set to a real `.com`)
- [ ] MX records verified (`/admin/domains → Verify MX`)
- [ ] Email webhook verified (carrier console → webhook URL is correct, signature passes)
- [ ] SMS provider configured (`SMS_PROVIDER` + keys)
- [ ] Real phone number inventory available (provider returns at least one E.164)
- [ ] SMS webhook verified (carrier console → webhook URL is correct, signature passes)
- [ ] Storage configured (`STORAGE_DRIVER=s3` + `S3_*` set, or local for staging)
- [ ] Stripe configured (`PAYMENT_PROVIDER=stripe` + Stripe keys, OR keep manual)
- [ ] CAPTCHA configured (recommended; not blocking in development)
- [ ] Production ads configured (client id set, `ads.test_mode=false`)
- [ ] Strong `AUTH_SECRET` configured (≥ 32 random bytes)
- [ ] Strong `CRON_SECRET` configured (≥ 16 random bytes)
- [ ] HTTPS enabled (TLS cert at the proxy; `APP_URL=https://...`)
- [ ] Cookies configured securely (`COOKIE_SECURE=true`)
- [ ] Rate limits enabled (seeded `RateLimitRule` rows present)
- [ ] Abuse protection enabled (IP bans + blocked senders reachable)
- [ ] Backups configured (host-managed Postgres; `/admin/backups` documents the policy)
- [ ] Error monitoring configured (tailable via `/api/health` and `/admin/audit`)

When every **critical** item is verified, the launch-checklist page
flips to **READY**.

## 5. Quick-start comparison

```bash
# ─── Free / local ──────────────────────────────────────────────────────
cp .env.example .env
npm install
npm run db:seed
npm run dev
# → http://localhost:3000 with mock everything

# ─── Production ────────────────────────────────────────────────────────
# 1. Provision managed Postgres + Redis + S3 + carrier accounts.
# 2. Set every variable in section 2.1 – 2.9 in the platform's secret
#    manager. Do NOT commit .env to Git.
# 3. Apply the schema:
npx prisma migrate deploy --schema=database/prisma/schema.prisma
# 4. Seed the database (roles, plans, currencies, feature flags, rate
#    limits, payment rails). The seed uses getEnv() so it reads the
#    same production environment as the running app.
npm run db:seed
# 5. Build and serve.
npm run build
npm run start
# 6. Schedule a cron POST to /api/v1/cron/tick with x-cron-secret.
```

Application code is unchanged between the two columns. The free setup
and the production setup differ only in the environment variables and
the platform-managed services behind them.
